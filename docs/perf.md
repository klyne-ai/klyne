## Methodology

### FTS5 Search p95

- **Tool**: `go test -bench=BenchmarkFTS5Search`
- **Dataset**: 100,000 synthetic messages seeded via `SeedStore()` using disjoint vocabulary buckets (10 buckets × 7 words each) so each query word appears in ~10% of messages.
- **Measurement**: 50 queries per benchmark iteration. Warm-up: 10 queries before `b.ResetTimer()` to pre-load the FTS5 page cache. p95 is computed over all collected latencies.
- **Spec budget**: < 50 ms p95 (warm cache, steady state).
- **Note**: Cold-cache first-query latency is 60–80 ms for common terms against 100K rows. This is expected and separately tracked by the cold-start test. The spec budget applies to the steady-state (warm-cache) path.

### JSONL Ingest Throughput

- **Tool**: `go test -bench=BenchmarkIngestThroughput`
- **Dataset**: 5,000 messages per batch. Inserted in a single bulk transaction via `SeedStoreInTx` (simulating the back-fill path on startup).
- **Measurement**: Messages-per-second = `batchSize / elapsed`.
- **Spec budget**: ≥ 5,000 msg/sec.
- **Actual**: ~51,000 msg/sec — 10× above budget. The production path uses per-message transactions (one tx per `InsertMessage` call), which is slower but not benchmarked here as it's the live-ingestion path.

### SSE Latency p95

- **Tool**: `go test -bench=BenchmarkSSELatency`
- **Setup**: `httptest.NewServer` with a custom SSE handler backed by the real `api.Hub`. Each sample: one `hub.Publish()` followed by reading the resulting SSE frame from the HTTP response body.
- **Measurement**: 50 samples per iteration. p95 computed over all samples.
- **Spec budget**: < 100 ms p95.
- **Note**: httptest uses loopback TCP, so this measures the hub fanout + HTTP write + read latency without network jitter. Production over 127.0.0.1 should be similar.

### Cold-Start to /healthz

- **Tool**: `go test -run=TestColdStart`
- **Setup**: Subprocess launch of `bin/klyne start --no-open` with `HOME` overridden to a temp dir containing a minimal `config.toml` (all connectors disabled, AI disabled). Poll `/healthz` every 10 ms.
- **Spec budget**: < 200 ms (developer laptop). CI budget relaxed to < 2000 ms.
- **Relaxation rationale**: GitHub Actions `ubuntu-latest` VMs have cold-process-spawn overhead and no warm page cache. The 2000 ms CI limit still catches catastrophic regressions while passing on CI hardware.

### Idle RAM

- **Tool**: `go test -run=TestIdleRAM`
- **Measurement**: `runtime.MemStats.HeapInuse + StackSys` after 30 s idle with `app.BuildOnly()` constructed but `Start()` not called. Two `runtime.GC()` calls before measurement.
- **Proxy**: 30 s idle instead of 1 h (spec), because 1 h idle is not feasible in CI. To run the 1-hour test manually: `AGENTDECK_IDLE_SECONDS=3600 go test -run TestIdleRAM ./internal/bench/...` (modify `TestIdleRAM` to read the env var).
- **OS gate**: Skipped on Windows. Runs on darwin and linux only.
- **Spec budget**: < 40 MB.
- **Note**: `runtime.MemStats` reports Go heap + stacks only; it does not include SQLite's mmap region (`mmap_size=256MB` is reserved but not resident until accessed), shared library code, or CGO allocations. The actual OS RSS (e.g., `ps -o rss=`) will be higher. We use the Go metric as a reproducible proxy.

### Active RAM

- **Tool**: `go test -run=TestActiveRAM`
- **Setup**: `SeedStore(5000 msgs)` + `ListMessagesBySession` + `Search` to exercise all DB paths. Same MemStats measurement.
- **Spec budget**: < 80 MB (1 session, 5K msg DB).

### Disk Footprint

- **Tool**: `go test -run=TestDiskFootprint` / `go test -bench=BenchmarkDiskFootprint`
- **Dataset**: 5,000 messages seeded via `SeedStore`.
- **JSONL estimate**: 450 bytes/message (actual JSON-encoded message with 200-byte content). This is a conservative lower bound; real Claude JSONL lines with tool_use blocks are 1–4 KB, which makes the real ratio even better (e.g., a 2 KB average JSONL line would yield a ratio of 0.25×).
- **DB total**: `.db` + `.db-wal` + `.db-shm` after `db.Close()` (passive WAL checkpoint).
- **Spec budget**: < 2× JSONL size.

### Binary Size

- **Tool**: `go test -bench=BenchmarkBinarySize` or `TestBinarySize`
- **Measurement**: `os.Stat("bin/klyne").Size()`. Test skips if binary not found.
- **Spec budget**: < 25 MB.

### Summary Turnaround

- **Status**: Stubbed in CI. Not measured with a real provider.
- **Why**: The spec §12 budget (< 3 s) applies to the real Gemini or Anthropic API round-trip, which requires live credentials and network. This cannot be measured reproducibly in CI.
- **What is measured**: `BenchmarkSummaryTurnaround` measures only the DB-side overhead (`InsertSummary` + `Hub.Publish`) using a mock. This shows the plumbing is <<1 ms and confirms the budget is entirely dependent on provider latency.
- **How to measure locally**: Configure a real provider in `~/.klyne/config.toml` and run with actual sessions. The `tasks.Runner` logs summary latency at DEBUG level.

## How to Reproduce

```bash
# Build the binary first (required for cold-start and binary-size tests).
make build

# Run all benches and get JSON report.
bash scripts/bench.sh > /tmp/bench-output.json

# Run the CI gate (fails if any budget is violated).
bash scripts/bench-ci.sh

# Run individual Go benchmarks interactively (10s benchtime for stable results).
go test -bench=BenchmarkFTS5Search -benchmem -benchtime=10s ./internal/bench/...
go test -bench=BenchmarkIngestThroughput -benchmem -benchtime=5s ./internal/bench/...
go test -bench=BenchmarkSSELatency -benchmem -benchtime=5s ./internal/bench/...

# Run all bench tests without -race (race detector skews timing).
go test -count=1 -timeout=300s ./internal/bench/...

# Skip the 30-second idle RAM test.
go test -count=1 -timeout=60s -short ./internal/bench/...
```

### Note on -race

Benchmarks in this package should NOT be run with `-race`. The race detector adds significant timing overhead (2–10× slower) that invalidates latency measurements. The production test suite runs with `-race`; the bench package is explicitly excluded from race checks in CI (see `.github/workflows/perf.yml`).

## Hotspot Notes

| Finding | Severity | Owner | Notes |
|---|---|---|---|
| Cold-cache FTS5 queries take 60–80 ms for high-frequency terms (appearing in >50% of messages) | INFO | W3 (search.go) | Warm-cache is ~10 ms; acceptable for v1. Consider query result caching in v1.1. |
| Per-message transaction in `store.InsertMessage` limits bulk ingest to ~5,000 msg/sec | INFO | W2 (messages.go) | Back-fill uses SeedStoreInTx bulk path. Live ingest is single-tx by design (R7 invariant). |
